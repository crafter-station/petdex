# Petdex Agent Notes

## Commands
- Use Bun for repo work: `bun install`, not `npm install`. Published CLI docs mention `npm`/`npx` for end users only.
- Recommended local app dev is `bun run dev:docker`; it boots local Postgres and Redis with shared Clerk dev defaults from `.env.dev`.
- A self-contained deployment lives in `Dockerfile` + `docker-compose.deploy.yml`: `docker compose -f docker-compose.deploy.yml up --build` serves the app at `127.0.0.1:3100` with in-process Clerk mocks — no external credentials. The mock-auth alias is baked in at **build** time (see the compose warning before relying on it for anything real); base images are digest-pinned.
- Maintainer dev is `bun dev` with `.env.local` copied from `.env.example`; this path expects Clerk, Postgres/Neon, R2, Upstash, Resend, AI Gateway, and ElevenLabs credentials.
- `bun run dev:mock` is deprecated and intentionally exits. Keep `.env.mock` only for targeted mock-backed tests or build checks.
- Root checks: `bun run check` for Biome, `bun run format` to write Biome fixes, `bun run build` for the Next app, `bun run test` for the full Bun suite, and `bun run i18n:check` after editing translation messages. There is no root `typecheck` script, but `app-ci.yml` runs `bunx tsc --noEmit`, so a type error fails CI even though nothing local catches it; run it yourself before pushing when you touch types. `app-ci.yml` also runs `bun run check` and `bun run i18n:check`, and `.githooks/pre-commit` runs `i18n:check` whenever a `src/i18n/messages/*.json` file is staged — the message files are the one thing Biome cannot judge, since a key that parses as a rich-text tag is valid JSON and correctly formatted while rendering as its own name. Use `bun run test` rather than a bare `bun test`: the raise lives in that script's `--timeout`, and a bare `bun test` never reads it, so it still aborts the specs that need more than Bun's 5s default. `bunfig.toml` cannot carry the raise instead: there is no `[test] timeout` key, and a `preload` calling `setDefaultTimeout` does not reach every file — measured at one of five.
- Focused tests use `bun run test path/to/file.test.ts`, which forwards the path and keeps the suite timeout. Tests that import `src/lib/db/client.ts` directly or indirectly need a usable `DATABASE_URL` or mock env: `bun run test --env-file=.env.mock src/lib/security.test.ts`. Neither `security.test.ts` nor the pet-search suites touch the db client today — the general rule is what to apply when a spec starts importing it.
- `mock.module` is process-wide, so a suite that stubs a module before importing anything that pulls it in is the only kind that runs correctly on its own. Seven integration suites run in isolated processes through `src/lib/collection-routes.test.ts` — four under `src/app/api/{cli,profile}`, plus `src/app/api/collections/[slug]/request/`, `src/lib/takedown-paths.integration.ts`, and `src/lib/submission-decisions-rename.integration.ts`. Six of them stub `@/lib/db/client` ahead of their `@/lib/collection-access` import for that reason — a stubbing suite that loads first in a root run masks the ordering, so run one alone (`bun run test 'src/app/api/profile/collections/[id]/route.integration.ts'`) after touching it. Their assertions therefore never execute the collection SQL: the cli/collections suite stubs `createOwnerCollection` (its POST path never calls `runCollectionMutation`), and the others stub the mutation runner. The rename suite is the exception — it owns a PGlite database and executes the rename batch's real SQL, asserting both the migrated rows and the statement order. When the point is to execute real SQL, use a suite that owns its PGlite connection (`src/lib/collection-empty-list.test.ts`, the rename suite). `src/lib/profile-name.integration.tsx` is an eighth process-wide-mocking suite outside that isolated runner — spread the real `@/lib/r2` module when stubbing it, a bare replacement starves the suites that load after it (this exact leak broke CI once).
- Do not run the whole root suite with `--env-file=.env.mock`: `PETDEX_MOCK=1` makes `packages/petdex-cli`'s `asset-hosts.test.ts` fail, because mock mode injects `mock.invalid` into the server-side asset allowlist the CLI pins against. Keep the env flag on focused root runs only.
- `packages/petdex-cli` and `packages/discord-bot` are independent packages, not root workspaces; run their own `bun install` and package scripts from inside each directory. Root `tsconfig.json` excludes `packages`.
- CLI package verification, run from `packages/petdex-cli`, is `bun run build && bun run typecheck`, plus `bun run test` for its suite. The build emits ignored `dist/petdex.js` and prepends the node shebang in `postbuild`. Use `bun run test` there for the same reason as the root: the `--timeout` lives in that script, and its spawn-a-CLI specs are slow enough to brush Bun's 5s default on a loaded machine. CI now runs `bun run test` there too, so the raise reaches it.
- Discord bot work stays in `packages/discord-bot`; use `bun run register`, `bun run dev`, or `bun run start` there with env from `packages/discord-bot/.env.example`.

## Architecture
- Main app routes live in `src/app/[locale]`; API routes live in `src/app/api`; shared server/domain code lives in `src/lib`; DB schema is `src/lib/db/schema.ts` with SQL migrations in `drizzle/`.
- This is Next `16.3.6` with newer conventions: `src/proxy.ts` is the middleware/proxy entrypoint, route/layout `params` are promises, and `src/app/layout.tsx` intentionally returns children while `[locale]/layout.tsx` owns `<html>`/`<body>` for locale `lang`. If touching framework APIs, prefer the installed Next docs under `node_modules/next/dist/docs/` over older assumptions.
- i18n locales are `en`, `es`, and `zh`; message files are under `src/i18n/messages/`, and `next-intl` is wired through `src/i18n/request.ts` plus the locale layout.
- Mock DB bootstrap tolerates migration/schema drift via fixups in `src/lib/mock/db.ts`; if schema fields are added and mock pages fail, update those fixups until a real migration lands.
- `drizzle.config.ts` hard-fails without `DATABASE_URL`; there are no root package scripts for migration generation or application, and many `scripts/apply-*` / `backfill-*` files are real-DB one-offs.
- Automated review/tag/sound paths use AI SDK model strings through Vercel AI Gateway (`AI_GATEWAY_API_KEY` in `.env.example`, read by `@ai-sdk/gateway` — there is no `OPENAI_API_KEY` fallback, so a bare OpenAI key does not make them work); avoid adding raw OpenAI client wiring to server paths. The exceptions that still read `OPENAI_API_KEY` directly are `src/lib/edit-policy.ts` (moderation kill switch) and the two image-generating scripts; `src/lib/wechat-qr-validator.ts` is dead code with no caller.

## Invariants
- Submission identity and credit data must come from verified Clerk session or CLI bearer token, never from request bodies. Keep this split in `src/lib/submissions.ts`, `/api/submit`, and `/api/cli/submit*`.
- State-changing browser endpoints should use `requireSameOrigin` from `src/lib/same-origin.ts`; CLI/server callers authenticate separately by bearer or service-side checks.
- Multi-statement writes go through `executeAtomicReturning` (`src/lib/db/client.ts`, over `src/lib/db/atomic.ts`), which keeps the statements **separate** and returns each one's rows. Separate statements are not a style choice: every CTE in a single statement shares the snapshot taken when that statement began, so a read placed after an advisory-lock wait still cannot see the row the lock was protecting, and a data-modifying CTE's UPDATE cannot see the INSERT in its sibling CTE. A single-statement CTE that "does it all" looks atomic and is not. The deployed driver is Neon HTTP, whose `transaction()` throws (`drizzle-orm/neon-http/session.js`), so the helper uses `db.batch` there and a callback transaction elsewhere — the batch path is what production runs. **Unverified locally**: that Neon's HTTP batch endpoint applies every statement in one transaction, and that it runs at the default isolation level, is taken from Neon's documentation; drizzle passes a hardcoded `queryConfig` and drops any `isolationLevel`, so there is no way to raise it. The local driver is postgres-js, so a `bun run test` run exercises the callback path, not the one production takes.
- User-supplied asset/avatar/external URLs are allowlisted in `src/lib/url-allowlist.ts`. Adding a new host usually also needs CSP updates in `next.config.ts` and regression coverage in `src/lib/security.test.ts`.
- CSP is explicit in `next.config.ts`; new Clerk/R2/analytics/media hosts must be added to the matching `script-src`, `connect-src`, `img-src`, `frame-src`, or `media-src` directive.
- Tailwind v4 tokens live in `src/app/globals.css` via `@theme inline` rather than `tailwind.config.*`; components should use semantic tokens such as `bg-surface`, `text-foreground`, and `border-border-base` instead of hardcoded `bg-white dark:*` pairs.
- `bun run generate-assets` rewrites app/public icons and OG images from `public/brand/petdex-mark.svg`, including `src/app/favicon.ico` because Next 16 prefers the app favicon.
- The `codex://pets/install` link in `src/lib/codex-desktop-link.ts` matches a parser inside ChatGPT.app that is not a documented contract: it rejects the whole URL on one unknown query param, and requires `spriteVersionNumber` to match the pet's own atlas version (1 for v1 8x9 sheets, 2 for v2 8x11) — never a hardcoded 2; v1 is the majority and the parser rejects a mismatched value. The modal that consumes it is behind a Statsig gate that is currently off, so a correct link lands and does nothing. Read `docs/chatgpt-pet-integration.md` before touching it or re-diagnosing it — it carries the parser, the gate id, and the recipe to re-derive both after an OpenAI update.
